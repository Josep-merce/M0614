Desplegament segur: Manager, HTTPS i port 8080 tancat

Deixaràs el servidor d'aplicacions a punt per a producció: el Tomcat Manager amb usuaris i rols, accessible només des de l'administrador; HTTPS a l'Apache que hi ha davant, amb redirecció automàtica des d'HTTP; i el port 8080 tancat a la xarxa perquè ningú es pugui saltar Apache.

RA RA3 CA 3.3 · 3.5 · 3.6 · 3.7
0

Objectius i prerequisits

En aquesta activitat aprendràs a:

  • Crear usuaris i rols de Tomcat a tomcat-users.xml.
  • Fer servir el Tomcat Manager per desplegar i retirar aplicacions a distància.
  • Restringir l'accés al Manager per IP a l'Apache.
  • Activar HTTPS a l'Apache que fa de proxy i redirigir tot l'HTTP cap a l'HTTPS.
  • Fer que Tomcat només escolti a 127.0.0.1, de manera que el port 8080 quedi tancat a l'exterior.

Prerequisit important

⚠️

Necessites l'Apache fent de proxy invers cap a Tomcat amb el host virtual www.app.local (A1.2). Comprova-ho abans: des del client, http://www.app.local/sample/ ha de funcionar.

1

Context i teoria mínima

El Tomcat Manager

El Manager és una aplicació que porta Tomcat (webapps/manager) per administrar les altres aplicacions sense entrar al servidor: llistar-les, desplegar-ne de noves, aturar-les, tornar-les a carregar o retirar-les. És molt pràctic i, per això mateix, molt perillós: qui hi entra pot posar el codi Java que vulgui al servidor.

Per això Tomcat el protegeix de dues maneres, i nosaltres n'hi afegirem una tercera:

  1. Usuari i contrasenya amb rol. Per defecte no hi ha cap usuari: ningú no hi pot entrar. Els crearem a tomcat-users.xml.
  2. Origen local. El fitxer webapps/manager/META-INF/context.xml només deixa entrar peticions de 127.0.0.1. Però, com que totes les peticions que passen per Apache arriben a Tomcat des de 127.0.0.1, aquesta protecció no distingeix els clients. Ho vas veure a l'A1.2.
  3. Restricció per IP a Apache. Com que Apache sí que veu la IP real, li direm que només deixi passar cap a /manager les peticions de l'administrador (192.168.1.20).

Rols del Manager

RolQuè permetRuta
manager-guiFer servir la interfície web, amb botons, des d'un navegador./manager/html
manager-scriptFer servir la interfície de text, pensada per a scripts i curl./manager/text/…
manager-statusNomés veure l'estat del servidor./manager/status
💡

La documentació de Tomcat recomana no donar manager-gui i manager-script al mateix usuari: si un usuari amb rol manager-script obrís una web maliciosa mentre té la sessió iniciada, aquesta web podria fer accions al Manager en nom seu. Per això crearem dos usuaris, un per a cada interfície.

HTTPS a la porta, HTTP a dins

El xifratge el farà Apache, que és qui parla amb el client. Entre Apache i Tomcat la connexió continuarà en HTTP, però no surt del servidor (127.0.0.1), així que ningú de la xarxa la pot llegir. Aquest esquema es diu terminació TLS al proxy.

Conceptes clau

ConcepteQuè és
tomcat-users.xmlFitxer de conf/ amb els usuaris, les contrasenyes i els rols de Tomcat. Es llegeix en arrencar.
RolNom d'un permís. Un usuari pot tenir-ne diversos; les aplicacions demanen rols, no usuaris.
Require ipDirectiva d'Apache que només deixa passar les peticions de les IP indicades. La resta reben 403 Forbidden.
<Location>Bloc d'Apache que aplica directives a una ruta de la URL (per exemple, /manager).
Terminació TLSEl proxy desxifra l'HTTPS i parla amb el backend en HTTP per una connexió interna.
address="127.0.0.1"Atribut del connector de Tomcat que el fa escoltar només dins del servidor.

Pas a pas guiat

💡

Cada pas ve dins d'una capsa de color que indica qui l'ha de fer: AdministradorServidorClient. Els fitxers de configuració no porten capsa.

Part 1 · Usuaris i rols del Manager

2.1 · Connecta't al servidor per SSH

Administrador
bash — administrador
ssh isard_ssh@192.168.1.10

➜ Obre una sessió de terminal xifrada al servidor per SSH.

💻→

A partir d'aquí, tot el que escrius s'executa al servidor, no a l'administrador. Per tornar a l'administrador quan acabis, escriu exit.

2.2 · Mira com es protegeix el Manager per defecte

Administrador → Servidor · per SSH
bash — administrador → servidor (SSH)
sudo grep -A2 '<Valve' /opt/tomcat/webapps/manager/META-INF/context.xml

➜ Mostra la Valve que filtra les peticions al Manager i les dues línies següents (-A2).

sortida esperada (aproximada)
  <Valve className="org.apache.catalina.valves.RemoteCIDRValve"
         allow="127.0.0.0/8,::1/128" />     # només des del mateix servidor

No la toquis. Segons la versió, pot sortir RemoteAddrValve amb una expressió regular; l'efecte és el mateix: només 127.0.0.1. Com que Apache es connecta des de 127.0.0.1, el filtre de debò el posarem a Apache.

2.3 · Crea els usuaris del Manager

Administrador → Servidor · per SSH
bash — administrador → servidor (SSH)
sudo nano /opt/tomcat/conf/tomcat-users.xml

➜ Obre el fitxer d'usuaris de Tomcat. Està ple d'exemples comentats (<!-- ... -->): no els toquis.

Baixa fins al final i, just abans de l'última línia </tomcat-users>, afegeix aquest bloc. Canvia les dues contrasenyes per unes de teves:

tomcat-users.xml
  <!-- AEA3 · A1.3 -->
  <role rolename="manager-gui"/>
  <role rolename="manager-script"/>
  <user username="gestor"      password="CONTRASENYA_GESTOR"      roles="manager-gui"/>      <!-- interfície web -->
  <user username="desplegador" password="CONTRASENYA_DESPLEGADOR" roles="manager-script"/>   <!-- curl / scripts -->
</tomcat-users>
⚠️

Les contrasenyes queden en clar dins del fitxer. Per això conf/ només la pot llegir l'usuari tomcat. Si una línia queda mal tancada (per exemple, sense />), Tomcat no podrà llegir el fitxer i no deixarà entrar ningú.

Administrador → Servidor · per SSH

Desa (Ctrl+O, Enter) i surt (Ctrl+X).

bash — administrador → servidor (SSH)
sudo systemctl restart tomcat

➜ Reinicia Tomcat perquè llegeixi els usuaris nous. Aquest fitxer només es carrega en arrencar.

bash — administrador → servidor (SSH)
curl -s -u desplegador:CONTRASENYA_DESPLEGADOR http://127.0.0.1:8080/manager/text/list

➜ Prova l'usuari des del mateix servidor, directament a Tomcat. -u envia l'usuari i la contrasenya. Ha de començar per OK - Listed applications for virtual host [localhost]. Si respon amb un error 401, l'usuari o la contrasenya no coincideixen.

Part 2 · HTTPS i restricció per IP a Apache

2.4 · Activa SSL i genera el certificat

Administrador → Servidor · per SSH
bash — administrador → servidor (SSH)
sudo a2enmod ssl

➜ Activa el mòdul ssl, que permet a Apache servir per HTTPS al port 443.

bash — administrador → servidor (SSH)
sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \
  -keyout /etc/ssl/private/app.key \
  -out /etc/ssl/certs/app.crt \
  -subj "/C=ES/ST=Barcelona/L=Barcelona/O=Institut La Merce/OU=DAW/CN=www.app.local" \
  -addext "subjectAltName=DNS:www.app.local,DNS:app.local"

➜ Genera el certificat autofirmat i la clau, com a l'AEA2, però en una sola ordre sense preguntes: -subj respon les dades del certificat (el CN és el nom del lloc) i -addext hi afegeix els noms alternatius, que és el que comproven els navegadors actuals.

2.5 · Reescriu el host virtual

Administrador → Servidor · per SSH
bash — administrador → servidor (SSH)
sudo nano /etc/apache2/sites-available/app.conf

➜ Obre el host virtual de l'A1.2.

Esborra'n tot el contingut i deixa'l així. Ara té dos blocs: el del 80 només redirigeix, i el del 443 fa tota la feina:

app.conf
# --- Port 80: només redirigeix a HTTPS ---
<VirtualHost *:80>
    ServerName  www.app.local
    ServerAlias app.local
    Redirect permanent / https://www.app.local/
</VirtualHost>

# --- Port 443: HTTPS + proxy cap a Tomcat ---
<VirtualHost *:443>
    ServerName  www.app.local
    ServerAlias app.local

    SSLEngine on
    SSLCertificateFile    /etc/ssl/certs/app.crt
    SSLCertificateKeyFile /etc/ssl/private/app.key

    ProxyRequests     Off
    ProxyPreserveHost On

    # El Manager només per a l'administrador
    <Location /manager>
        Require ip 192.168.1.20
    </Location>
    ProxyPass /host-manager !               # aquest no el fem servir: continua sense publicar

    ProxyPass        / http://127.0.0.1:8080/
    ProxyPassReverse / http://127.0.0.1:8080/

    ErrorLog  ${APACHE_LOG_DIR}/app_error.log
    CustomLog ${APACHE_LOG_DIR}/app_access.log combined
</VirtualHost>
💡

Fixa't que ja no hi ha ProxyPass /manager !: ara el Manager sí que passa a Tomcat, però el bloc <Location /manager> fa que Apache l'aturi amb un 403 abans de reenviar-lo si la petició no ve de 192.168.1.20.

Administrador → Servidor · per SSH

Desa i surt.

bash — administrador → servidor (SSH)
sudo apache2ctl configtest

➜ Revisa la sintaxi. Ha de respondre Syntax OK.

bash — administrador → servidor (SSH)
sudo systemctl restart apache2

➜ Reinicia Apache: cal restart perquè has activat un mòdul nou (ssl) i s'ha d'obrir el port 443.

Part 3 · Tancar el 8080 a l'exterior

2.6 · Fes que Tomcat només escolti a 127.0.0.1

Administrador → Servidor · per SSH
bash — administrador → servidor (SSH)
sudo nano /opt/tomcat/conf/server.xml

➜ Obre la configuració principal de Tomcat. Busca el connector amb Ctrl+W i escriu Connector port="8080".

Afegeix-hi l'atribut address="127.0.0.1". Deixa la resta d'atributs tal com estiguin:

server.xml
    <Connector port="8080" address="127.0.0.1" protocol="HTTP/1.1"     <!-- afegeix address -->
               connectionTimeout="20000"
               redirectPort="8443"
               ... />                                                   <!-- la resta, igual -->
Administrador → Servidor · per SSH

Desa i surt.

bash — administrador → servidor (SSH)
sudo systemctl restart tomcat

➜ Reinicia Tomcat perquè torni a obrir el connector, ara només a l'adreça interna.

bash — administrador → servidor (SSH)
sudo ss -tlnp | grep -E ':(80|443|8080) '

➜ Comprova on escolta cada servei. Espera uns segons si el 8080 encara no surt.

sortida esperada
LISTEN 0 511  *:80                 *:*  users:(("apache2",...))   # Apache HTTP (redirecció)
LISTEN 0 511  *:443                *:*  users:(("apache2",...))   # Apache HTTPS
LISTEN 0 100  [::ffff:127.0.0.1]:8080  *:*  users:(("java",...))  # ⚠ EL MÉS IMPORTANT: Tomcat només dins del servidor
💡

A l'A1.0 i l'A1.1 el 8080 sortia com *:8080 (totes les adreces). Ara només surt a 127.0.0.1: des de la xarxa ningú s'hi pot connectar, però Apache sí, perquè és al mateix servidor. En un servidor real, a més, s'hi afegiria un tallafoc (per exemple ufw) que només deixés entrar el 22, el 80 i el 443.

Part 4 · Proves

2.7 · Prova l'HTTPS des del client

Client
🔎 Comprova-ho al navegador http://www.app.local/sample/

Escriu-la amb http. El navegador ha de saltar sol a https://www.app.local/sample/ i mostrar l'avís de seguretat del certificat autofirmat. Accepta'l (a Firefox: Avançat → Accepta el risc). Ha de sortir l'aplicació d'exemple. Clica el cadenat: el certificat és per a www.app.local i l'ha emès Institut La Merce.

🔎 Comprova-ho al navegador https://www.app.local/manager/html

Des del client, ha de sortir Forbidden (You don't have permission to access this resource). Ni tan sols et demana usuari: Apache t'atura per la IP abans d'arribar a Tomcat.

🔎 Comprova-ho al navegador http://192.168.1.10:8080

A l'A1.2 funcionava. Ara ha de fallar amb No es pot connectar: el 8080 ja no és accessible des de la xarxa.

2.8 · Fes servir el Manager des de l'administrador

Administrador

Surt de l'SSH (exit). L'administrador també ha de conèixer el nom www.app.local:

bash — administrador
echo '192.168.1.10   www.app.local   app.local' | sudo tee -a /etc/hosts

➜ Afegeix la línia al final de /etc/hosts de l'administrador. tee -a l'afegeix amb permisos de sudo sense esborrar res.

bash — administrador
curl -k -u desplegador:CONTRASENYA_DESPLEGADOR https://www.app.local/manager/text/list

➜ Llista les aplicacions desplegades a través del Manager, per HTTPS i des de la IP permesa. -k accepta el certificat autofirmat.

sortida esperada (l'ordre pot variar)
OK - Listed applications for virtual host [localhost]   # ⚠ EL MÉS IMPORTANT
/:running:0:ROOT
/sample:running:0:sample
/manager:running:0:manager
/docs:running:0:docs
/examples:running:0:examples
/host-manager:running:0:host-manager

Ara desplega una aplicació nova sense entrar al servidor. Primer, descarrega el .war d'exemple a l'administrador:

bash — administrador
wget https://tomcat.apache.org/tomcat-10.1-doc/appdev/sample/sample.war

➜ Descarrega l'aplicació d'exemple oficial a la carpeta on ets.

bash — administrador
curl -k -u desplegador:CONTRASENYA_DESPLEGADOR -T sample.war "https://www.app.local/manager/text/deploy?path=/demo"

➜ -T puja el fitxer al Manager, que el desplega amb la ruta /demo. Ha de respondre OK - Deployed application at context path [/demo]. Les cometes calen perquè la URL porta un ?.

🔎 Comprova-ho al navegador https://www.app.local/demo/

Des del client: ha de sortir la mateixa aplicació d'exemple, ara a la ruta /demo. L'has desplegada a distància, sense tocar webapps.

bash — administrador
curl -k -u desplegador:CONTRASENYA_DESPLEGADOR "https://www.app.local/manager/text/undeploy?path=/demo"

➜ Retira l'aplicació /demo. Ha de respondre OK - Undeployed application at context path [/demo].

💡

Si l'administrador té navegador, obre https://www.app.local/manager/html amb l'usuari gestor: veuràs la llista d'aplicacions amb els botons Start, Stop, Reload i Undeploy, i un formulari per pujar un .war.

Verificació

Client
bash — client
curl -I http://www.app.local/sample/

➜ Demana la pàgina per HTTP i mostra només la capçalera.

sortida esperada
HTTP/1.1 301 Moved Permanently                # ⚠ redirecció
Server: Apache/2.4.NN (Ubuntu)
Location: https://www.app.local/sample/       # cap a l'HTTPS
bash — client
for u in /sample/ /manager/html /host-manager/html; do
  printf '%-20s %s\n' "$u" "$(curl -k -s -o /dev/null -w '%{http_code}' https://www.app.local$u)"
done
curl -m 5 -s -o /dev/null http://192.168.1.10:8080/ && echo "8080: obert" || echo "8080: tancat"

➜ El bucle demana tres rutes per HTTPS i escriu només el codi de cada resposta. L'última línia intenta connectar al 8080 amb un límit de 5 segons (-m 5) i escriu obert o tancat segons si ho aconsegueix.

sortida esperada
/sample/             200      # l'aplicació funciona per HTTPS
/manager/html        403      # ⚠ el client no pot entrar al Manager
/host-manager/html   404      # no es publica
8080: tancat                  # ⚠ no es pot connectar al 8080
Administrador
bash — administrador
curl -k -s -o /dev/null -w 'sense usuari: %{http_code}\n' https://www.app.local/manager/html
curl -k -s -o /dev/null -w 'amb gestor:   %{http_code}\n' -u gestor:CONTRASENYA_GESTOR https://www.app.local/manager/html

➜ La mateixa pàgina del Manager, primer sense credencials i després amb l'usuari gestor.

sortida esperada
sense usuari: 401             # Apache el deixa passar (IP correcta), però Tomcat demana usuari
amb gestor:   200             # ⚠ EL MÉS IMPORTANT: IP permesa + usuari amb rol manager-gui

Llista de comprovació

  • tomcat-users.xml té els usuaris gestor (manager-gui) i desplegador (manager-script).
  • http://www.app.local redirigeix amb un 301 a https://www.app.local.
  • L'aplicació funciona per HTTPS amb el certificat de www.app.local.
  • Des del client, /manager/html dona 403; des de l'administrador, 401 sense usuari i 200 amb gestor.
  • L'administrador ha desplegat i retirat /demo amb curl i l'usuari desplegador.
  • ss mostra Tomcat només a 127.0.0.1:8080 i el client no s'hi pot connectar.
⚠️

Si l'administrador rep 403 al Manager, Apache no veu la seva IP com a 192.168.1.20: comprova-la amb ip a i revisa el Require ip. Si rep 502 Proxy Error o 503, Tomcat no respon a 127.0.0.1:8080: revisa l'address de server.xml i mira sudo journalctl -u tomcat -n 30.
