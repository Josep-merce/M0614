Resum de l'AEA6

Documentació, control de versions i integració contínua. Aquest és el fil sencer de les 7 activitats, en ordre, sobre el mateix repositori compartit aea6-usuari1-usuari2.

A0

Primers passos amb Git i GitHub

Individual, abans de començar a treballar en parella. Cadascú instal·la VS Code, Git i la GitHub CLI (gh) al seu ordinador, crea el seu compte de GitHub, configura el seu nom i correu (git config), i s'autentica amb gh auth login. Amb un repositori d'usar i llençar (practica-git), practica els 4 comandaments bàsics: crea un fitxer, en fa commit i push, i simula el canvi d'un company editant el fitxer directament des de GitHub i fent pull per baixar-lo. Al final, esborra aquest repositori de pràctiques.

Criteri: 6.5
A1

Primeres passes amb Git/GitHub

Ja en parella, amb el repositori de veritat. El Propietari crea aea6-usuari1-usuari2 a GitHub (amb un README inicial), hi puja un index.html senzill, i afegeix el Col·laborador com a col·laborador del repositori. El Col·laborador clona el repositori i comprova que veu exactament el mateix contingut. Per tancar l'activitat, el Col·laborador omple el README (que fins ara només tenia el títol) i el puja; el Propietari fa pull i el rep — practicant el flux en tots dos sentits.

Criteri: 6.5
A2

Treball en parella amb branques

Cadascú crea la seva pròpia branca: el Propietari feature/header (hi afegeix una capçalera a index.html), el Col·laborador feature/footer (hi afegeix un peu de pàgina). Cada branca es puja i s'obre com a Pull Request separat. La revisió és creuada: cadascú revisa i fusiona el Pull Request de l'altre, mai el propi. Com que els dos han editat parts diferents del fitxer, els dos merges es fan sense conflicte. Finalment, cadascú crea un token d'accés personal a GitHub per autenticar-se des del terminal sense fer servir la contrasenya del compte.

Criteris: 6.5, 6.6
A3

Documentació amb Markdown

S'aprèn la sintaxi bàsica de Markdown (títols, negreta, llistes, blocs de codi, taules). Tots dos treballen a la mateixa branca docs/readme: el Propietari hi escriu la secció d'instal·lació de Git al README.md, el Col·laborador hi afegeix la de configuració i ús. Com que és una sola branca compartida, només cal un Pull Request (a diferència de l'A2) per portar-ho tot a main.

Criteris: 6.3, 6.7
A4

Eines de documentació automàtica

Activitat autònoma: no depèn de cap fitxer d'activitats anteriors. Cadascú instal·la Node.js i npm si encara no els tenia. El Propietari crea js/main.js amb dues funcions petites (campOmplert i mostrarMissatge), cadascuna documentada amb un comentari JSDoc (/** ... */). S'inicialitza el projecte amb npm init, s'instal·la JSDoc com a dependència de desenvolupament, es genera automàticament una web de documentació (docs/) amb npx jsdoc, i es puja tot (incloent package.json i docs/) en un sol Pull Request compartit, igual que a l'A3.

Criteris: 6.1, 6.2
A5

Disseny visual i documentació col·laborativa

El Propietari crea style.css (tipografia, colors, marges) i l'enllaça a index.html. El Col·laborador es posa al dia amb git fetch + checkout de la mateixa branca design/wiki, fa una captura de pantalla de la pàgina ja amb estil, i documenta el resultat a la Wiki de GitHub (pàgina "Home"): primer el Propietari hi escriu la presentació del projecte, després el Col·laborador hi afegeix la captura i un fragment del CSS. És una segona manera de documentar, diferent de la generació automàtica de l'A4.

Criteris: 6.3, 6.4
A6

Integració contínua

El Propietari crea .github/workflows/ci.yml línia a línia, un workflow de GitHub Actions que, a cada push, comprova que index.html existeix i que js/main.js no té errors de sintaxi. A diferència de la resta d'activitats, el Pull Request s'obre abans (no al final): es queda obert mentre el Col·laborador hi afegeix un comentari inofensiu (veu la CI en verd), després provoca un error de sintaxi a propòsit (veu la CI fallar en vermell, amb l'error real de node --check), i finalment el corregeix (torna a verd). Només llavors es fusiona el Pull Request, tancant tota l'AEA6.

Criteri: 6.8
